# 二、名词含义说明

## 2.1架构演进类名词
### 单体架构

**一句话：所有功能都写在一个程序里，打包成一个包部署。**

论文里的原系统就是“Java 单体架构加单库部署”：登记、缴税、缴费、缮证、查询等模块都在一个系统里，共用一张数据库。好处是开发简单，坏处是牵一发动全身：缴费模块内存泄漏，整个平台停摆 40 分钟；改一个小功能，全系统都要重新发布。

### SOA

**一句话：把系统拆成一个个“服务”，服务之间通过接口调用。**

SOA 是“面向服务的架构”，比单体进一步。它想把登记、缴税、缴费等拆成独立服务，但传统 SOA 往往需要一个中央总线来连接。

### 企业服务总线（ESB）

**一句话：传统 SOA 里的“中央通信总线”，所有服务都接到它上面。**

比如 A 服务要调 B 服务，不直接调，而是把请求发给 ESB，由 ESB 转发、转换协议、做安全控制。问题是：ESB 成了中心，一旦挂了全部调用中断；而且它支持的协议很多、配置复杂，开发成本高。论文里把它作为“方案二”否掉了。

### 微服务架构

**一句话：把系统拆成多个小而独立的服务，每个服务独立开发、部署、扩容、故障隔离。**

论文里拆成了 8 个服务：登记、缴税、缴费、缮证、查询、权籍调查、电子证照、通知。每个服务有自己的数据库，可以单独升级，一个服务坏了不至于全站瘫痪。

### 业务域 / DDD 限界上下文

**一句话：按业务边界来拆，而不是按技术分层来拆。**

DDD 是“领域驱动设计”。限界上下文可以理解成“一块业务边界清晰的领域”。比如“登记”和“缴税”是两块不同业务，就拆成两个服务。不是把“所有 Controller 放一起、所有 Service 放一起”那种按技术拆。

### 接口契约 / 数据归属

**一句话：服务之间说好怎么调用，以及数据归谁管。**

比如登记服务是“业务主数据的所有者”，缴税、缴费不能直接去改登记服务的数据库，只能通过登记服务提供的接口拿数据。这就是“数据归属”。

## 2.2服务治理与通信类名词

### 服务注册发现

**一句话：服务启动后自动登记地址，调用方按服务名找到它。**

论文用 Nacos 做服务注册发现。比如缴税服务启动后告诉 Nacos：“我在 192.168.1.10:8080”。登记服务要调缴税，就问 Nacos：“缴税服务在哪？”Nacos 返回地址。这样服务动态上下线，不用手写死 IP。

### 配置中心

**一句话：把配置集中管理，改配置不用重新打包。**

Nacos 同时做配置中心。比如限流阈值、数据库地址、开关参数，放在 Nacos 里，服务启动时拉取，改完可以动态生效。

### API 网关

**一句话：所有外部请求的统一入口。**

前端不直接调各个微服务，而是先到 API 网关。网关负责鉴权、限流、路由转发。论文里前端经 API 网关统一接入，网关承担鉴权、限流与路由。

### REST + OpenFeign

**一句话：服务之间用 HTTP 接口同步调用。**

REST 是一种轻量接口风格，通常用 HTTP + JSON。OpenFeign 是一个 Java 组件，让你像调本地方法一样调远程 REST 接口。论文里“同步调用采用 REST 加 OpenFeign”。

### RocketMQ

**一句话：消息队列，用来异步传递消息。**

比如登记完成后，发一条消息到 RocketMQ，通知缴税、缴费去处理。调用方不用等对方处理完，解耦、削峰。论文里“异步通知采用 RocketMQ”。

### 同步走 HTTP、异步走消息

**一句话：需要立即拿结果的用 HTTP 调；不需要立即等结果的，发消息。**

比如查询登记详情要马上返回，就走 HTTP。登记完成后通知电子证照生成，可以慢一点，就发消息。

### SkyWalking 链路追踪

**一句话：记录一个请求经过了哪些服务、每段花了多久。**

比如用户查登记详情，请求经过网关、查询服务、登记服务、电子证照服务。SkyWalking 能把整条链路画出来，帮你定位哪一段慢。论文里用它发现 P99 延迟上升。

## 2.3容错与弹性类名词

### 服务雪崩

**一句话：一个服务挂掉，导致调用它的服务也挂，像雪崩一样扩散。**

比如缴税服务响应很慢，登记服务大量线程被卡住，最后登记服务也崩，整个平台不可用。所以要熔断降级。

### 熔断

**一句话：发现某个服务一直失败或超时，就暂时不再调它，直接走备用逻辑。**

像保险丝，电流过大就断开。论文里：登记服务调缴税服务超时则熔断，3 秒内返回“缴税模块繁忙请稍后重试”。

### 降级

**一句话：服务不可用时，返回一个兜底结果，保证主流程不卡死。**

比如缴税暂时不可用，就先提示“稍后重试”，而不是让整个登记流程一直等。

### 限流

**一句话：限制单位时间内的请求量，防止把服务打垮。**

论文对登记、缴税两个热点服务配置独立限流阈值。新政窗口期请求暴增，超过阈值就排队或拒绝，保护系统。

### 实例 / 扩容

**一句话：一个服务可以启动多个副本，副本就是实例。**

比如登记服务平时 2 个实例，新政窗口期扩到 8 个实例，处理能力更强。查询服务维持 2 个实例不动，节省资源。

### K8s / 容器化

**一句话：把服务打包成容器，用 K8s 统一调度、部署、扩缩容。**

容器可以理解成一个轻量、标准化的“软件盒子”，里面装好代码和运行环境。K8s 是容器编排平台，负责启动、停止、扩容、故障重启。

### 水平自动伸缩

**一句话：根据 CPU、内存等指标，自动增加或减少实例数量。**

论文里配置为 CPU 超过 70% 时自动扩容。流量大了自动加机器，流量小了自动减。



## 2.4数据一致性类名词

### 跨服务数据一致性

**一句话：一个业务要改多个服务的数据，怎么保证最终都对。**

论文例子：“二手房转移登记”要依次完成登记受理、契税核定、登记费缴纳，这三个动作在不同服务里。如果登记成功、缴税失败，数据就不一致。

### 强一致 / 最终一致

- **强一致**：任何时刻所有服务看到的数据都一样，通常要分布式事务锁，性能差、复杂。

- **最终一致**：中间短暂不一致，但经过补偿后，最终所有数据都对。

论文选择最终一致，避免分布式事务锁。

### 本地消息表

**一句话：在业务数据库里加一张“待发消息表”，业务数据和消息一起提交。**

登记服务在本地数据库事务里，同时写入业务数据和“待发送消息”。这样业务成功了，消息一定不会丢。然后后台任务把消息投递到 RocketMQ。

### 事务回查

**一句话：消息投递失败或状态不明时，回头查数据库确认，再补发。**

本地消息表 + 定时任务 + 回查补偿，保证消息最终发出去。

### 幂等

**一句话：同一个请求处理多次，结果和一次一样。**

比如缴费消息重复消费，不能扣两次钱。消费方要做幂等处理，通常用唯一业务号去重。

### 事务型消息

**一句话：消息队列本身支持“消息发送”和“本地事务”绑定，比本地消息表更自动。**

论文最后说“后续拟引入事务型消息进一步收窄不一致窗口”。



## 2.5部署与发布类名词

### CI/CD

**一句话：持续集成、持续交付/部署。**

代码提交后自动编译、测试、构建镜像、部署。论文里“代码合入主干后自动构建镜像”。

### 灰度发布

**一句话：新版本先给一小部分用户用，没问题再全量。**

比如先放 5% 流量到新版本，观察稳定后再逐步扩大。出问题影响面小。

### 一键回滚

**一句话：发现新版本有问题，快速切回旧版本。**

CI/CD 流水线支持回滚，减少故障时间。

### 镜像

**一句话：容器化后的软件包，包含代码和运行环境。**

K8s 根据镜像启动容器实例。

### 主干

**一句话：团队共用的主代码分支。**

代码合入主干后触发流水线，自动构建、测试、部署。


## 2.6性能与优化类名词

### P99 延迟

**一句话：99% 的请求都在这个耗时内完成，只有最慢的 1% 会超过它。**

P99 从 200 毫秒升到 420 毫秒，说明慢请求变多了。优化后回落到 260 毫秒。

### 序列化

**一句话：把对象转成字节流，方便网络传输。**

比如 Java 对象转成 JSON。每次跨服务调用都要序列化和反序列化，次数多了就慢。

### 鉴权凭证透传

**一句话：网关鉴权一次后，把用户身份凭证传给下游，下游不用重复校验。**

论文里“避免每跳重复校验”，减少开销。

### 聚合服务

**一句话：把多个服务的查询合并成一个接口，减少网络往返。**

原来查“登记详情 + 证照”要调 4 个服务，现在聚合服务一次返回。

### CQRS

**一句话：读写分离，写模型和读模型分开。**

写服务负责业务操作，读服务专门做查询。论文里把高频报表下沉为独立的只读视图服务。

### 只读视图服务 / 异步物化

**一句话：把多个服务的数据提前汇总成一张只读表，查询直接查它。**

通过订阅各服务变更事件，异步更新这张表。避免跨库联查，也不影响写入链路。

### 跨库联查

**一句话：一条 SQL 同时查多个数据库的表。**

单体时一张库可以 join，拆成微服务后每个服务独立数据库，就不能直接 join 了。所以用 CQRS 视图服务解决。
