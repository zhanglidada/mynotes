

# 一、指令运行流程：

**cpu指令执行流程主要分为以下几个阶段：**
## 1. 取指（Instruction Fetch）

CPU 根据程序计数器 PC 指向的地址，从指令缓存/内存中取出下一条指令，放进指令寄存器。取指后 PC 通常指向下一条指令。

- 顺序执行时：PC = PC + 指令长度；
    
- 遇到跳转/分支时：PC 要改成跳转目标地址；
    
- 如果是间接跳转，目标地址可能要等后面阶段才知道，所以 CPU 需要预测。

## 2. 译码（Decode）

CPU 解析取到的指令，弄清：

- 这是什么操作：加法、load、store、跳转、调用等；
    
- 操作数在哪里：寄存器、立即数、内存地址；
    
- 要写回哪个寄存器。
    

现代 CPU 还会把复杂指令拆成多个微操作，并做寄存器重命名等处理。

## 3. 执行（Execute）

CPU 在算术逻辑单元 ALU 中执行实际运算，比如：

- 整数加减、逻辑运算；
    
- 计算内存地址；
    
- 比较条件，决定条件分支是否跳转；
    
- 计算间接跳转的目标地址。
    

如果是 load/store 指令，这里通常计算访存地址。

## 4. 访存（Memory Access）

只有 load/store 等访存指令需要这个阶段：

- load：从数据缓存/内存读数据；
    
- store：把数据写入数据缓存/内存。
    

其他指令可以跳过这个阶段。


## 5. 写回（Writeback）

把执行结果写回寄存器堆，或者把 store 的数据真正写入内存系统。指令执行结果到这里基本产生。

## 6. 提交/退休（Commit / Retire）

现代乱序执行 CPU 通常还有“提交”阶段。指令虽然可能乱序执行，但必须按程序顺序提交，保证程序语义正确。提交后，指令的结果正式生效，异常和中断也在这个阶段处理。

## 7. PC 更新与分支

每条指令执行后，PC 要更新：

- 普通指令：PC 指向下一条；
    
- 直接跳转：目标地址在指令里，容易知道；
    
- 条件分支：要判断条件是否成立；
    
- 间接跳转：目标从寄存器/内存取，CPU 往往要预测。
    

如果预测错误，CPU 要清空流水线中错误路径上的指令，从正确地址重新取指，这就是**误预测惩罚**。

## 8.总结
CPU 执行指令的大致流程是：**按 PC 取指 → 译码 → 执行 → 访存 → 写回 → 提交**；同时更新 PC。现代 CPU 用流水线并行执行多条指令，遇到分支要预测，间接跳转目标难预测，预测错会造成流水线冲刷和性能损失。

# 二、流水线

流水线一种**时间上的重叠执行机制**。把一条指令的执行拆成多个阶段（取指、译码、执行、访存、写回），每个阶段由专门的硬件负责。理想情况下，每个时钟周期都有一条新指令进入流水线，同时有指令在不同阶段推进。这样虽然单条指令的延迟（latency）还是那么多周期，但吞吐率（throughput）提高到接近每周期完成一条。

**流水线执行的各个阶段：**
- IF：Instruction Fetch，取指
    
- ID：Instruction Decode，译码/读寄存器
    
- EX：Execute，执行
    
- MEM：Memory Access，访存
    
- WB：Write Back，写回

**流水线寄存器位于相邻阶段之间：**

- IF/ID：IF和ID之间的寄存器
    
- ID/EX：ID和EX之间的寄存器
    
- EX/MEM：EX和MEM之间的寄存器
    
- MEM/WB：MEM和WB之间的寄存器

## 1. 流水线是什么

流水线（pipeline）本质是**把一条指令的执行拆成多个阶段，让多条指令在不同阶段同时推进**。它不是“一条指令从头到尾更快”，而是“==🟠单位时间完成的指令更多==”。


经典五级流水线：
```
IF 取指 → ID 译码 → EX 执行 → MEM 访存 → WB 写回
```


理想情况下，每个时钟周期都有一条新指令进入 IF，同时：

- 第 1 条在 WB；
    
- 第 2 条在 MEM；
    
- 第 3 条在 EX；
    
- 第 4 条在 ID；
    
- 第 5 条在 IF。
    

就像工厂流水线：每道工序由专门工位负责，产品一件件往下传。单件产品经过全部工位的时间没变短，但每周期都能出一件。

## 2. 流水线是一组硬件吗？存了什么？

**是。** 流水线主要由两部分硬件组成：

1. **各阶段的功能单元**：取指单元、译码器、ALU、数据缓存接口、寄存器堆写端口等；
    
2. **阶段之间的流水线寄存器**（pipeline registers），经典五级里叫：
    
    - `IF/ID`：保存取到的指令和 PC；
        
    - `ID/EX`：保存译码后的操作数、控制信号、目标寄存器号；
        
    - `EX/MEM`：保存 ALU 结果、要写内存的数据、目标寄存器号；
        
    - `MEM/WB`：保存从内存读出的数据或 ALU 结果、目标寄存器号。
        

**流水线寄存器保存的是“正在途中的指令”在某一阶段产生的状态**，每个周期从上一级锁存到下一级。

它不是“提前把当前指令的所有信息一次性加载好”，而是**逐级传递**：

- IF 取到指令，放入 `IF/ID`；
    
- ID 从 `IF/ID` 读指令，译码，读寄存器，把控制信号和操作数放入 `ID/EX`；
    
- EX 从 `ID/EX` 读，算结果，放入 `EX/MEM`；
    
- MEM 从 `EX/MEM` 读，访存，结果放入 `MEM/WB`；
    
- WB 从 `MEM/WB` 读，写回寄存器堆。
    

有些信息确实要到后面才有，比如 load 的数据要到 MEM 阶段才从缓存读出来。

## 3. 为什么流水线存在预测失败的代价？

关键在于：**取指阶段必须每个周期都知道“下一条指令在哪”**，否则流水线就会断流。

普通指令好办：PC 加指令长度。直接跳转也好办：目标在指令里，译码后就知道。但遇到**间接跳转**，目标在寄存器或内存里，可能要等 EX 阶段甚至 load 完成才知道。==🟡但是取指阶段不能停，只能**猜**下一条指令地址，然后沿着猜的路径继续取指==。

于是问题来了：猜错时，流水线里已经装了一批**错误路径上的指令**。

```
周期1: IF 取到分支指令
周期2: 分支进 ID，IF 继续取“预测路径”的下一条
周期3: 分支进 EX，发现预测错；但 IF、ID 已经又取了两条错误指令
```

这时必须：

1. **冲刷（flush/squash）** 流水线中错误路径上的指令；
    
2. 把 PC 改成正确目标；
    
3. 从正确地址重新取指；
    
4. 重新经过 IF、ID，才能到达 EX 继续执行。
    

从“发现错误”到“正确指令重新填满流水线”的这段时间，就是**误预测惩罚**。流水线越深，已经取入的错误指令越多，重新填满越慢，惩罚越大。

所以==🔴预测失败的代价==不是“跳转指令本身慢”，而==🟠是：**错误路径的指令已经进入流水线，占了工位，必须丢掉；正确路径的指令还没取进来，要重新走一遍前面的阶段==。**

这也回答了你“会不会提前加载信息”的问题：取指阶段确实会**沿着预测路径提前取后续指令**，并把它们放进流水线寄存器；但这些指令可能是错的，发现错后就要全部作废。流水线寄存器的存在，既是流水线能重叠执行的基础，也是误预测时“要清理的在途状态”的来源。

## 4. 为什么不能只删掉错误指令、保留正确指令？

因为错误路径上的指令可能已经：

- 改变了分支预测器状态；
    
- 占用了重命名表、ROB 等资源（乱序 CPU）；
    
- 甚至乱序执行了部分操作（但不会提交）。
    

更重要的是，**正确路径的指令还没被取进来**。你没法“保留”不存在的指令，只能从正确地址重新取指，重新走 IF、ID、EX。==🟠流水线越深，重新启动越贵==。

还要区分两个概念：

- **停顿（stall）**：数据冒险，比如后一条指令等前一条的结果，流水线暂停，但不丢弃指令；
    
- **冲刷（flush）**：控制冒险预测错，丢弃错误路径指令，重新取指。
    

预测失败属于后者，代价通常比普通停顿大。

## 5. 回到解释器：为什么间接跳转预测失败特别贵？(和vm的解释器关联)

解释器每条 VM 指令都要 dispatch：

```
lw   $2,0($4)   # 从 VM 指令流取出下一个 handler 地址
addu $4,$4,4
j    $2         # 间接跳转
```

`j $2` 的目标要等 `lw` 从内存读出 `$2` 才知道。取指阶段等不了，只能猜“下一个 handler 在哪”。猜错就冲刷流水线，重新取指。

而解释器每执行一条简单 VM 指令就遇到一次这种间接跳转，所以：

- 间接分支比例高；
    
- 目标难预测，尤其 switch dispatch 所有 opcode 共用一个跳转点；
    
- 误预测频繁，流水线反复冲刷；
    
- 累计起来可占运行时间一半以上。
    

论文里说“这些分支消耗超过一半运行时间”，本质就是：**流水线为了不断流，沿着预测路径提前取指；预测错后，错误路径的指令已经进入流水线，必须丢弃并重新填满，而解释器每执行一条 VM 指令就触发一次这种风险。**


# 三、指令跳转：

直接跳转和间接跳转的核心区别只有一个：**跳转目标地址从哪里来、什么时候能知道**。两者都是改变程序计数器 PC，让 CPU 从另一个地址继续取指令；区别在于目标是“指令里写死的”还是“运行时从寄存器/内存里取出来的”。

## 1 直接跳转：
**定义**：跳转目标地址由跳转指令本身直接给出，或者可以由指令中的编码直接算出来。常见形式是：

- 绝对地址：`jmp 0x401000`
    
- PC 相对偏移：`jmp L1`、`beq $t0,$t1,L2`
    
- 直接函数调用：`call func`

MIPS：
```
j    L2          # 直接跳转到 L2
beq  $2,$0,L2    # 条件直接分支：条件成立就跳到 L2
```

X86:
```
jmp  .L1         # 直接相对跳转
je   .L2         # 条件直接跳转
call foo         # 直接调用，目标 foo 编码在指令中
```

关键点：
1. 目标地址是静态的：同一条直接跳转指令，正常情况下总是跳向同一个目标地址。
2. 目标在取指/解码阶段就可以知道：CPU 不需要等寄存器或内存里的值算出来，就可以开始从目标地址取指。
3. 条件直接分支仍有“方向预测”问题：目标虽然已知，但“跳不跳”取决于条件，CPU 要预测条件是否成立。预测错也会冲刷流水线。
4. 无条件直接跳转通常不需要目标预测：目标已知，CPU 可以直接重定向取指；但可能仍需等解码等阶段。

所以直接跳转并不是“一定没有代价”，而是目标地址容易早知道；条件直接分支的主要风险是方向预测错误。

## 2 间接跳转：
**定义**：跳转目标地址不是指令里写死的，而是运行时从寄存器或内存中取出/计算出来的。指令只告诉 CPU“去某个寄存器或内存位置取目标”。

MIPS:
```
jr   $ra         # 跳到 $ra 中的地址
j    $2          # 跳到 $2 中的地址
```

X86:
```
jmp  *%rax       # 跳到 rax 中的地址
call *(%rax)     # 间接调用：目标地址从内存取
ret              # 返回：目标地址从栈中取，可视为特殊间接分支
```

ARM/RISC-V：
```
br   x0          # 间接跳转
jalr x0, 0(x1)   # 间接跳转/调用
```


**关键点**：

1. **目标地址是动态的**：同一条间接跳转指令，不同次执行可能跳向不同目标。例如函数指针调用、虚函数调用、switch 跳转表、解释器 dispatch。
    
2. **目标通常要等执行阶段才知道**：目标可能来自寄存器，也可能要先做一次 load 从内存读出来。CPU 取指阶段就需要下一条指令地址，所以必须“猜”目标。
    
3. **间接跳转通常需要目标预测**：分支目标缓冲 BTB 缓存“这个分支上次跳到哪里”；两级预测器用全局历史+分支地址预测目标。预测错就是目标误预测，要冲刷流水线。
    
4. **间接跳转往往比直接跳转更难预测**：尤其是一个间接跳转点对应很多目标时（多目标/超多目标间接分支）。


## 直接跳转和间接跳转对比：
| 维度       | 直接跳转                           | 间接跳转                             |
| -------- | ------------------------------ | -------------------------------- |
| 目标地址来源   | 指令编码中直接给出/可直接算出                | 寄存器或内存中的值                        |
| 目标何时可知   | 取指/解码阶段通常可知                    | 执行阶段、甚至等 load 完成才可知              |
| 目标是否静态   | 同一指令通常固定目标                     | 同一指令可能有多个动态目标                    |
| 主要预测问题   | 条件直接分支：预测“跳不跳”                 | 预测“跳到哪里”                         |
| 典型例子     | `j L1`、`beq ... L2`、`call foo` | `j $2`、`jmp *%rax`、`ret`、函数指针调用  |
| 解释器中的角色  | handler 内部的控制流、跳回 dispatch 循环等 | VM 指令 dispatch，即跳到下一条 VM 指令的处理代码 |
| **性能风险** | 方向误预测                          | 目标误预测、目标地址依赖 load                |


# 三、分支预测：
## 1.直接分支预测（猜方向）：


直接分支（Direct Branch）的**目标地址是固定的**，它作为一个立即数或偏移量，直接编码在指令自身当中。因此，预测器无需猜测“要去哪”，任务简化为预测“**是否会跳转**”（即方向：Taken / Not Taken）。

这通常由**条件方向预测器（Conditional Direction Predictor）** 负责，现代处理器的核心是基于历史的动态预测：

- **TAGE预测器**：通过多张使用**不同长度全局分支历史**的表，来捕捉从近期到远期的复杂相关性。预测时，它会选择匹配到**最长历史**的表的结果，以获得最高的准确率。
    
- **基础结构**：最底层的逻辑常基于**两位饱和计数器**，根据历史执行结果来预测本次方向，避免因单次偶然结果而频繁改变预测。

## 2.间接分支预测（猜目标）：
间接分支（Indirect Branch）的目标地址来自**寄存器的值**，在运行时可能不断变化。这意味着**同一条指令可能对应多个不同的目标**，因此预测的核心任务是**预测目标地址**。

对应的**间接分支预测器**需要更复杂的机制：

- **传统方案**：主要依赖**分支目标缓冲区（BTB）**，缓存该指令最近一次的目标地址。但面对多目标场景时，简单的BTB会力不从心。
    
- **现代方案 (ITTAGE)**：借鉴了TAGE的思想，使用全局分支/路径历史来索引多个预测表，以捕捉不同上下文下的目标地址模式，从而精准预测间接跳转的目的地。它的本质是一个针对分支目标地址的**值预测器**。
    
- **特殊成员：返回地址栈 (RAS)**：对于函数返回（`return`）这类规律性极强的间接分支，硬件会使用一个专用的**返回地址栈**来精确预测返回地址，这是间接分支预测的一种高效特例。
