# 一、指令执行流程

> 本笔记是论文解读的**前置知识**，覆盖：指令执行流程 → 流水线（含超标量与内存依赖）→ 跳转类型 → 分支预测 → 让间接分支变快的架构手段。
> 对应的论文笔记：[[《The Structure and Performance of Efficient Interpreters》]]

经典五级流水线把一条指令的执行拆成 5 个阶段：**取指 → 译码 → 执行 → 访存 → 写回**。下面按这 5 级讲，最后补两个容易混淆的点：“提交/退休”和“PC 更新”——它们都不是流水级。

## 1.1 取指（Instruction Fetch）

CPU 根据程序计数器 PC 指向的地址，从指令缓存（I-Cache）/内存中取出下一条指令，放进 `IF/ID` 流水线寄存器。取指后 PC 通常指向下一条指令。

- 顺序执行时：PC = PC + 指令长度（MIPS 定长 4 字节，即 PC+4；x86 变长，长度不固定）；
- 遇到跳转/分支时：PC 要改成跳转目标地址；
- 如果是间接跳转，目标地址可能要等后面阶段才知道，所以 CPU 必须预测。

> 经典五级模型里没有单独的“指令寄存器 IR”，IF 的结果直接锁存在 `IF/ID` 中。

## 1.2 译码（Decode）

CPU 解析取到的指令，弄清：

- 这是什么操作：加法、load、store、跳转、调用等；
- 操作数在哪里：寄存器、立即数、内存地址；
- 要写回哪个寄存器。

现代 CPU 在译码阶段还会做：把复杂指令拆成多个微操作（x86 的译码产物就是 μop），以及切分变长指令的边界（x86 需要）。

注意：**寄存器重命名不在译码阶段**，它在译码之后的独立 rename 阶段（见 §1.6）。

## 1.3 执行（Execute）

CPU 在算术逻辑单元 ALU 中执行实际运算，比如：

- 整数加减、逻辑运算；
- 计算内存地址；
- 比较条件，决定条件分支是否跳转；
- 计算间接跳转的目标地址。

如果是 load/store 指令，这里通常计算访存地址。

## 1.4 访存（Memory Access）

只有 load/store 等访存指令需要在这个阶段做实际的内存访问：

- load：从数据缓存（D-Cache）/内存读数据；
- store：把数据写入数据缓存/内存。

其他指令不是“跳过”这个阶段，而是**正常流过 MEM 级但该级不做有用工作**；`EX/MEM → MEM/WB` 的流水线寄存器照样要打拍。

## 1.5 写回（Writeback）

只做一件事：把结果写回寄存器堆。数据来源二选一：

- ALU 计算结果（算术/逻辑指令）；
- 从内存读出的数据（load 指令，经 `MEM/WB` 传上来）。

注意两点：

- **store 没有写回动作**：它的数据在访存阶段就已经写进缓存/内存了；
- 写回的目标是寄存器号（rd 或 rt），由 `ID/EX`、`EX/MEM`、`MEM/WB` 一路带下来。

## 1.6 补充：提交/退休（Commit / Retire，只有乱序 CPU 才有）

经典五级流水线是顺序执行的，WB 写回完成即生效，没有单独的提交阶段。现代乱序执行 CPU 才有：指令可以乱序执行，但必须按程序顺序提交，保证程序语义正确（精确异常）。提交之后，指令的结果才算正式生效，异常和中断也在这个点处理。

寄存器重命名同样是乱序 CPU 的机制，发生在译码之后的 rename 阶段，和“顺序提交”一起构成乱序执行的两端。

## 1.7 补充：PC 更新与分支（这不是一个流水级）

PC 每个周期在 IF 阶段更新（顺序时 PC ← PC+4）；分支/跳转解析后，PC 被改写成目标地址。不同指令的更新规则：

- 普通指令：PC 指向下一条；
- 直接跳转：目标地址在指令里，容易知道；
- 条件分支：要判断条件是否成立（方向预测）；
- 间接跳转：目标从寄存器/内存取，CPU 往往要预测（目标预测）。

> 如果预测错误，CPU 要清空流水线中错误路径上的指令，从正确地址重新取指，这就是**误预测惩罚**（详见[[#2.4 为什么流水线存在预测失败的代价？]]）。

## 1.8 小结

CPU 执行指令的大致流程是：**按 PC 取指 → 译码 → 执行 → 访存 → 写回**，同时更新 PC。现代 CPU 用流水线并行执行多条指令，遇到分支要预测，间接跳转目标难预测，预测错会造成流水线冲刷和性能损失。乱序 CPU 在此基础上再加一层“乱序执行 + 顺序提交”。

# 二、流水线

## 2.1 流水线是什么

流水线（pipeline）是一种**时间上的重叠执行机制**：把一条指令的执行拆成多个阶段，每个阶段由专门的硬件负责，让多条指令在不同阶段同时推进。

它不等于“一条指令从头到尾更快”，因为单条指令的延迟（latency）没变，变的是**吞吐率（throughput）提高到接近每周期完成一条**。就像工厂流水线：每道工序由专门工位负责，产品一件件往下传，单件产品经过全部工位的时间没变短，但每个周期都能出一件。

经典五级流水线：

```
IF 取指 → [IF/ID] → ID 译码 → [ID/EX] → EX 执行 → [EX/MEM] → MEM 访存 → [MEM/WB] → WB 写回
```

方括号里的就是流水线寄存器。时空图（理想情况，无冒险）：

| 指令/周期 | 1 | 2 | 3 | 4 | 5 | 6 | 7 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| I1 | IF | ID | EX | MEM | WB |  |  |
| I2 |  | IF | ID | EX | MEM | WB |  |
| I3 |  |  | IF | ID | EX | MEM | WB |
| I4 |  |  |  | IF | ID | EX | MEM |
| I5 |  |  |  |  | IF | ID | EX |

第 5 个周期起，每个周期都有一条指令完成（WB 出队）。

## 2.2 流水线的硬件组成

**流水线是一组硬件，主要由两部分组成**：阶段之间的流水线寄存器，以及各阶段的功能单元。

### 2.2.1 流水线寄存器

相邻阶段之间有流水线寄存器，经典五级里叫 `IF/ID`、`ID/EX`、`EX/MEM`、`MEM/WB`。

它们的作用是：每个时钟周期把上一阶段产生的结果“锁存”下来，供下一阶段在下一个周期使用，同时让上一阶段腾空出来继续处理新指令。它们**不是“一个寄存器”，而是一组寄存器/锁存器**，按字段保存一条在途指令在某一阶段结束时的状态：

| 流水线寄存器   | 位置       | 保存什么                                                                                                                 | 交给谁                 |
| -------- | -------- | -------------------------------------------------------------------------------------------------------------------- | ------------------- |
| `IF/ID`  | IF ↔ ID  | 取到的指令字（32/64 位指令编码）；该指令的 PC 值（MIPS 里锁存的是 PC+4）                                                                       | ID 阶段译码、读寄存器        |
| `ID/EX`  | ID ↔ EX  | 译码后的控制信号（ALU 操作码、是否写寄存器、是否读/写内存、分支类型、跳转信号）；从寄存器堆读出的两个源操作数（rs、rt 的值）；符号/零扩展后的立即数；目标寄存器号（rd 或 rt）；PC 值                 | EX 阶段取操作数和控制信号      |
| `EX/MEM` | EX ↔ MEM | **ALU 计算结果**（算术结果，或访存地址）；**要写入内存的数据**（store 的源数据，通常来自 rt）；目标寄存器号；控制信号（写寄存器/读内存/写内存/mem-to-reg）；分支相关的分支目标地址、条件结果、是否跳转 | MEM 阶段执行 load/store |
| `MEM/WB` | MEM ↔ WB | 从内存读出的数据（load 结果）或 ALU 结果（非 load 指令的最终值）；目标寄存器号；控制信号（是否写寄存器、mem-to-reg）                                              | WB 阶段写回寄存器堆         |

> `IF/ID` 里的 PC 值后续用于计算分支目标（PC+4 + offset）、异常处理，以及 `jal`/`jalr` 的链接地址。**PC 本身不会被写回**；真正写进寄存器的是 PC+4（作为链接地址），这也是 `jal` 能做函数调用的原因。

### 2.2.2 各阶段的功能单元

每个流水级都有自己的功能单元，多条在途指令按周期轮流使用它们：

| 阶段  | 主要功能单元                                                  |
| --- | ------------------------------------------------------- |
| IF  | 取指单元、PC 寄存器、I-Cache 接口                                  |
| ID  | 译码器、寄存器堆读端口                                             |
| EX  | ALU（算术运算、地址生成、条件比较、跳转目标计算都在这里）。这是经典五级模型；现代 CPU 常把分支解析提前 |
| MEM | D-Cache 接口                                              |
| WB  | 寄存器堆写端口                                                 |

这些单元被多条在途指令**分时复用**——同一周期两条指令抢同一个单元，就是结构冒险（见 §2.3.1）。

### 2.2.3 逐级传递的过程

回到流水线寄存器：**每一级只锁存“下一级需要的字段”**，逐级传递，不是一次把整条指令的所有信息都带上。

- IF 取到指令，放入 `IF/ID`；
- ID 从 `IF/ID` 读指令，译码，读寄存器，把控制信号和操作数放入 `ID/EX`；
- EX 从 `ID/EX` 读，算结果，放入 `EX/MEM`；
- MEM 从 `EX/MEM` 读，访存，结果放入 `MEM/WB`；
- WB 从 `MEM/WB` 读，写回寄存器堆。

有些信息确实要到后面才有，比如 load 的数据要到 MEM 阶段才从缓存读出来。

> 流水线寄存器的存在，既是流水线能重叠执行的基础，也是误预测时“要清理的在途状态”的来源——想清楚这一点，就明白为什么冲刷不是免费的。

## 2.3 流水线冒险（Hazard）

流水线不是免费的：指令之间会互相牵制，这类问题统称**冒险**。分三类，是理解“停顿 vs 冲刷”的前提。

### 2.3.1 结构冒险（Structural Hazard）

两条指令在同一周期争抢同一个硬件资源。例如：

- 简化实现中寄存器堆只有单端口：ID 读操作数、WB 写结果要在同一周期发生，就会冲突；解决办法是双端口或“前半拍写、后半拍读”。经典五级 MIPS 用 2 读 1 写的寄存器堆避免了这个问题。
- 取指和数据访问共用同一个存储器（冯·诺依曼结构）：把 I-Cache 和 D-Cache 分开（哈佛结构）就是为了消除它。

### 2.3.2 数据冒险（Data Hazard）

后一条指令要用前一条还没写回的结果。最常见的是 RAW（读后写）：

```
add $1, $2, $3
sub $4, $1, $5    # 要用 $1，但 add 的结果可能还没写回
```

解决办法：

- **转发/旁路（forwarding/bypass）**：不等写回，直接把 `EX/MEM`、`MEM/WB` 里的结果转给需要它的 ALU 输入；
- **停顿（stall）+ 气泡**：转发也解决不了的情况，典型是 load-use：

```
lw  $2, 0($4)
add $3, $2, $5    # load 的数据要到 MEM 末尾才有，即使有转发也必须停 1 拍
```

- 编译器调度（把无关指令插到中间）填满空拍。

### 2.3.3 控制冒险（Control Hazard）

分支/跳转改变 PC 带来的冒险：取指已经沿着旧 PC 取了后面的指令，结果发现要跳走。处理方式只能是**预测**：猜对了没有代价，猜错了要冲刷（详见 §2.4）。

### 2.3.4 停顿（stall）vs 冲刷（flush）

这两个概念容易混，区别如下：

| | 停顿（stall） | 冲刷（flush / squash） |
| --- | --- | --- |
| 触发原因 | 数据冒险、结构冒险 | 控制冒险（分支预测错） |
| 已取进流水线的指令 | 保留，只暂停/插入气泡 | 全部作废、丢弃 |
| PC 怎么变 | 不变（或重取同一地址） | 改成正确目标后重取 |
| 代价 | 通常几拍 | 通常更大，取决于“取指→分支解析”的级数 |

## 2.4 为什么流水线存在预测失败的代价？

关键在于：**取指阶段几乎每个周期都要知道“下一条指令在哪”**，否则流水线就断流。

普通指令好办：PC 加指令长度。直接跳转也好办：目标在指令里，译码后就知道。但遇到**间接跳转**，目标在寄存器或内存里，可能要等 EX 阶段甚至 load 完成才知道。**但取指不能停——停了就浪费吞吐，所以只能猜**下一条指令地址，然后沿着猜的路径继续取指。

于是问题来了：猜错时，流水线里已经装了一批**错误路径上的指令**。

```
周期1: IF 取到分支指令
周期2: 分支进 ID，IF 继续取"预测路径"的下一条
周期3: 分支进 EX，发现预测错；但 IF、ID 已经又取了两条错误指令
```

这时必须：

1. **冲刷（flush/squash）** 流水线中错误路径上的指令；
2. 把 PC 改成正确目标；
3. 从正确地址重新取指；
4. 重新经过 IF、ID，才能到达 EX 继续执行。

从“发现错误”到“正确指令重新填满流水线”的这段时间，就是**误预测惩罚**。

这里有一个常被说错的地方：惩罚大小**主要取决于“从取指到分支解析之间隔了几级”**，而不是流水线总深度。分支解析越靠后，已经取进流水线的错误指令就越多。所以现代 CPU 会尽量把分支解析提前到 ID 甚至取指阶段，并在取指阶段就用 BTB 直接给出目标地址——这才使得很深的流水线仍然能跑好。

> 论文还补了一个反直觉的点：**乱序执行不但没有消掉惩罚，反而可能把真实惩罚抬得更高**。因为在乱序机器上，间接分支要等到给它提供目标地址的那条 load 完成（走到写回）才能解析；如果这条 load 因为缺数据被拖晚了，分支的解析点就跟着被拖晚，错误路径上的指令也就取进来了更多（论文 §5.1）。所以“惩罚 = 取指到解析的级数”这句话在乱序机器上要理解成**动态值**，取决于依赖链多久能出结果。

> 所以“预测失败的代价”不是“跳转指令本身慢”，而是：**错误路径的指令已经进入流水线，占了工位，必须丢掉；正确路径的指令还没取进来，要重新走一遍前面的阶段。**

这也回答了一个常见疑问：“会不会提前加载信息？”——取指阶段确实会沿着预测路径提前取后续指令，并把它们放进流水线寄存器；但这些指令可能是错的，发现错后就要全部作废。

## 2.5 为什么不能只删掉错误指令、保留正确指令？

因为错误路径上的指令可能已经：

- 改变了分支预测器状态；
- 占用了重命名表、ROB 等资源（乱序 CPU）；
- 甚至乱序执行了部分操作（但不会提交）。

更重要的是，**正确路径的指令还没被取进来**。你没法“保留”不存在的指令，只能从正确地址重新取指，重新走 IF、ID、EX。流水线越深、分支解析越晚，重新启动越贵。

## 2.6 回到解释器：为什么间接跳转预测失败特别贵？

### 2.6.1 两种 dispatch 风格，预测难度完全不同

**switch dispatch**：所有 opcode 共用一个间接跳转点。

```c
switch (opcode) {
  case ADD: r = a + b; break;
  /* ... */
}
// 编译成一次 jump table 间接跳转：所有 opcode 都从这同一个 PC 跳向几十上百个目标
```

BTB 只看到同一个分支 PC，却要对应几十上百个目标 → 目标预测率很低。

**threaded code（线索化代码）**：handler 地址被内联在 VM 指令流里，每个 handler 末尾都有自己的那份 dispatch 代码。

```asm
lw   $2, 0($4)   # 从 VM 指令流取出下一个 handler 的地址
addu $4, $4, 4   # VM 的"PC"向前走 4 字节
jr   $2          # 间接跳转：跳到下一个 handler
```

`jr $2` 的目标要等 `lw` 从内存读出 `$2` 才知道；取指阶段等不了，只能猜“下一个 handler 在哪”，猜错就冲刷流水线、重新取指。

这段还有两个细节容易写错：必须先 `lw` 再 `addu`（先把地址读出来，再让 VM 的 IP 前进）；跳转用 **`jr`**，MIPS 的 `j` 是 26 位立即数目标，不能跟寄存器。

每个 handler 都有自己的跳转点，分支 PC 各不相同 → BTB 可以按 PC 区分，预测好得多。

> 线索化代码还分两种，论文里 Gforth 用的是**间接线索化（indirect threaded code, ITC）**：VM 指令流里存的不是 handler 地址，而是**指向 handler 地址的指针**，所以在 `lw`（取 handler 地址）和间接跳转之间还要**多一条 load**。代价是多一条指令；好处是地址多一层间接，改一个入口单元就能让所有引用它的地方换 handler（便于运行时打补丁、跟踪、特化）。论文 Fig.3 展示的是**直接线索化（direct threaded code, DTC）**的 3 条指令序列（fetch + 推进 IP + 跳转），这也是“每条 VM 指令 3 条原生指令的 dispatch 开销”这个说法的出处（论文 §7 用它对比 Java 需要 16 条指令做 fetch/decode）。Gforth 若换成 DTC，每条间接分支还能再少一条 load，间接分支占比会更高（论文脚注 9）。

小结一句：**同样是“每条 VM 指令一次间接跳转”，switch dispatch 是“单点对多目标”（难预测），threaded code 是“多点对少目标”（易预测）。** 这是论文里最关键的一组对比。

### 2.6.2 坏消息：即使换成 threaded code，比例依然高

- 间接分支比例高：解释器每执行一条 VM 指令就要经历一次间接跳转；
- 目标仍然多，BTB 仍然容易冲突；
- 误预测频繁，流水线反复冲刷；
- 累计起来，误预测惩罚可以占到运行时间的很大比例。

论文的实测数字（SimpleScalar 2.0，模拟 MIPS 类架构，四发射超标量，L1 load 延迟 2 周期；分支预测不命中惩罚按 4 周期与 13 周期两档测）：

| 指标 | 数值 | 出处 |
| --- | --- | --- |
| 间接分支占已执行指令比例（高效解释器） | **3.2%–13%** | 摘要、Fig.5 |
| 对照：间接分支预测研究常用基准的上限 | 至多 **2.1%** | §3 |
| 每条间接分支（≈每条 VM 指令）对应的原生指令数 | gforth **7.6–9.6**、ocaml **8.8–15.8**、scheme48 **30.5**、yap **17.9–18.5** | Fig.5（原文列名 inst./ind.） |
| BTB / BTB2 在 threaded code 上的误预测率 | BTB **57%–63%**、BTB2 **50%–61%** | Fig.6 |
| BTB / BTB2 在 switch dispatch 上的误预测率 | Ocaml、Scheme48 高达 **98%**；Yap **81%–86%** | Fig.6 |
| 两级间接分支预测器的误预测率 | 通常 **<10%**（即准确率 >90%） | §5.2.1、§8 |
| 惩罚 4 周期：gforth-benchgc 无预测 vs 两级预测 | 9 周期 vs 3.5 周期每条间接分支 → **2.55 倍**，即无预测时 **61%** 时间耗在间接分支上 | §5.2.2 |
| 惩罚 13 周期：同一基准 | 无预测 vs 两级预测相差 **4.77 倍**（**79%** 时间在间接分支上） | §5.2.2 |
| switch dispatch 相对 threaded code 的额外开销 | 最多慢 **2.02 倍**（ocamllex，BTB2，惩罚 4 周期） | §5.2.4、Fig.11 |
| switch 比 threaded code 多执行的指令数 | Ocaml 多 **5.9–6.6** 条/VM 指令，Yap 多 **7.9** 条；总指令数最多差 **1.76 倍**（ocamllex） | §3 |

真实机器交叉验证（Athlon，用性能计数器，误预测惩罚 10 周期）：gforth-benchgc 上 **55%** 的 taken branch 误预测，平均每 **20** 个周期就有一次误预测 → 大约一半时间花在误预测上；这与 SimpleScalar 上 BTB 的 60% 间接分支误预测率对得上（§5.2.7）。

> 论文的核心论点：解释器的瓶颈不是“指令条数多”，而是**每执行一条 VM 指令就要承担一次高风险间接跳转**，流水线的误预测惩罚把这份风险放大成了主要开销。

## 2.7 超标量：每周期不止一条指令

前面几节讲的都是“每周期一条”的经典模型。真实 CPU 是**超标量（superscalar）**：每个周期可以取多条、译码多条指令，并把它们分派到多个功能单元上并行执行，这个能力叫指令级并行（ILP）。所以吞吐率可以超过 1 条/周期。

论文用的 SimpleScalar 2.0 配置就是一台**四发射**的乱序机器，还有几条具体限制值得记住，因为论文的结论都建立在这些数字上：

| 配置项 | 论文取值 | 对读论文的意义 |
| --- | --- | --- |
| 发射宽度 | 4 条指令/周期 | threaded code 的 dispatch 只有 3 条原生指令，理论上能被并行摊平 |
| L1 cache 端口 | 只有 2 个 | 两条 load 加一条 store 就要多占一拍，访存是瓶颈之一 |
| L1 load 延迟 | 2 周期 | 从缓存取指令地址/handler 指针不是零成本 |
| 发射时的限制 | 除宽度外还有常规约束（如端口数） | 带宽不是无限的，不能指望“再多发几条就没事” |

另外，论文实验里的**条件方向预测器**配成“bimodal + 两级自适应”的组合预测器，两张表各 4096 项、两级部分历史长度 12；返回地址栈扩到 64 项。而**间接分支**那一侧它手动对比了 no prediction / profile-guided / BTB / BTB2 / 两级（历史 1–8 个目标）五种方案——这正是第四章、第五章各小节讨论的预测器方案的实验对照来源。

这一节存在的意义是：论文 §5.2.3 有一个**预期落空**的实验——本来以为“给足取指/译码带宽，dispatch 依赖链短，就能跑在前面，靠重叠把误预测惩罚掩盖掉”，结果曲线几乎是线性的，掩盖不了。要理解为什么掩盖不了，需要的不是发射宽度，而是**内存依赖**（见 §5.6）。

## 2.8 小结

流水线的收益是吞吐率，代价是冒险；控制冒险只能靠预测，预测错就要冲刷。**记住两句话：“停顿不丢指令、冲刷丢指令”；“惩罚取决于取指到分支解析的级数”**——这是读懂解释器性能论文的前提。另外记住：真实机器是超标量的，但带宽再大也解决不了控制冒险，只能靠预测或者降低惩罚（第五章）。

# 三、指令跳转

直接跳转和间接跳转的核心区别只有一个：**跳转目标地址从哪里来、什么时候能知道**。两者都是改变程序计数器 PC，让 CPU 从另一个地址继续取指令；区别在于目标是“指令里写死的”还是“运行时从寄存器/内存里取出来的”。

## 3.1 直接跳转

**定义**：跳转目标地址由跳转指令本身直接给出，或者可以由指令中的编码直接算出来。常见形式是：

- 汇编里写成绝对地址：`jmp 0x401000`（注意 x86 的实际编码仍是 PC 相对偏移 `E9 rel32`，真正的“绝对直接跳转”在 x86 里基本只有 far jmp）；
- PC 相对偏移：`jmp L1`、`beq $t0,$t1,L2`；
- 直接函数调用：`call func`。

MIPS：

```asm
j    L2          # 直接跳转（J 型：26 位立即数左移 2 位，拼上 PC 高 4 位）
beq  $2,$0,L2    # 条件直接分支：条件成立就跳到 L2
```

x86：

```asm
jmp  .L1         # 直接相对跳转
je   .L2         # 条件直接跳转
call foo         # 直接调用，目标 foo 编码在指令中
```

关键点：

1. 目标地址是静态的：同一条直接跳转指令，正常情况下总是跳向同一个目标地址。
2. 目标在译码阶段就可以知道：CPU 不需要等寄存器或内存里的值算出来，就可以开始从目标地址取指。
3. 条件直接分支仍有“方向预测”问题：目标虽然已知，但“跳不跳”取决于条件，CPU 要预测条件是否成立。预测错也会冲刷流水线。
4. 无条件直接跳转通常不需要目标预测：目标已知，CPU 可以直接重定向取指；但可能仍需等译码等阶段。

所以直接跳转并不是“一定没有代价”，而是目标地址容易早知道；条件直接分支的主要风险是方向预测错误。

## 3.2 间接跳转

**定义**：跳转目标地址不是指令里写死的，而是运行时从寄存器或内存中取出/计算出来的。指令只告诉 CPU“去某个寄存器或内存位置取目标”。

MIPS：

```asm
jr   $ra         # 跳到 $ra 中的地址（函数返回）
jr   $2          # 跳到 $2 中的地址（解释器 dispatch 的常用形式）
```

> MIPS 里寄存器跳转是 `jr`；`j` 是 26 位立即数目标，不能跟寄存器。

x86：

```asm
jmp  *%rax       # 跳到 rax 中的地址
call *(%rax)     # 间接调用：目标地址从内存取
ret              # 返回：目标地址从栈中取，可视为特殊间接分支
```

ARM64（x0 是通用寄存器，AArch64 没有硬连线的零寄存器）：

```asm
br   x0          # 间接跳转
blr  x1          # 间接调用：跳转并把返回地址写入 x30
```

RISC-V（x0 恒为 0）：

```asm
jalr x1, 0(x5)   # 间接调用：目标 = x5+0，返回地址写入 x1
jalr x0, 0(x6)   # 间接跳转：rd=x0，丢弃返回地址
```

关键点：

1. **目标地址是动态的**：同一条间接跳转指令，不同次执行可能跳向不同目标。例如函数指针调用、虚函数调用、switch 跳转表、解释器 dispatch。
2. **目标通常要等执行阶段才知道**：目标可能来自寄存器，也可能要先做一次 load 从内存读出来。CPU 取指阶段就需要下一条指令地址，所以必须“猜”目标。
3. **间接跳转通常需要目标预测**：分支目标缓冲 BTB 缓存“这个分支上次跳到哪里”；一个跳转点对应多个目标时，用多目标 BTB 或 ITTAGE 这类更复杂的目标预测器。
4. **间接跳转往往比直接跳转更难预测**：尤其是一个间接跳转点对应很多目标时（多目标/超多目标间接分支）。

## 3.3 直接跳转 vs 间接跳转

| 维度 | 直接跳转 | 间接跳转 |
| --- | --- | --- |
| 目标地址来源 | 指令编码中直接给出/可直接算出 | 寄存器或内存中的值 |
| 目标何时可知 | 译码阶段通常可知 | 执行阶段、甚至等 load 完成才可知 |
| 目标是否静态 | 同一指令通常固定目标 | 同一指令可能有多个动态目标 |
| 主要预测问题 | 条件直接分支：预测“跳不跳” | 预测“跳到哪里” |
| 典型例子 | `j L1`、`beq ... L2`、`call foo` | `jr $2`、`jmp *%rax`、`ret`、函数指针调用 |
| 解释器中的角色 | handler 内部的控制流、跳回 dispatch 循环等 | VM 指令 dispatch，即跳到下一条 VM 指令的处理代码 |
| **性能风险** | 方向误预测 | 目标误预测、目标地址依赖 load |

## 3.4 小结

一句话记住本章的区别：**直接跳转的目标从指令编码里来，间接跳转的目标从寄存器/内存里来**。这一条决定了三件事：

- 目标**何时可知**：直接跳转译码阶段就知道，间接跳转要等执行、甚至等一次 load；
- **要不要预测目标**：直接跳转不用，间接跳转必须；
- **预测难点**：直接跳转（条件分支）难在“跳不跳”，间接跳转难在“跳到哪里”。而解释器的 dispatch 恰好是后者，且目标多、分布随 opcode 变化——这正是论文要解决的问题。

# 四、分支预测

分支预测要回答两个问题：**往哪跳（目标）** 和 **跳不跳（方向）**。直接分支的目标已知，只需要回答后者；间接分支两个都要回答，而且“目标”这一问更难。

## 4.1 直接分支预测（猜方向）

直接分支（Direct Branch）的**目标地址是固定的**，它作为一个立即数或偏移量，直接编码在指令自身当中。因此，预测器无需猜测“要去哪”，任务简化为预测“**是否会跳转**”（即方向：Taken / Not Taken）。

这通常由**条件方向预测器（Conditional Direction Predictor）** 负责，现代处理器的核心是基于历史的动态预测：

- **两位饱和计数器**：最基础的一层，根据历史执行结果来预测本次方向，避免因单次偶然结果而频繁改变预测（强跳转/弱跳转/弱不跳转/强不跳转四态）。
- **两级自适应预测器**（Yeh & Patt）：第一级用分支历史（局部历史或全局历史）选出“上下文”，第二级在每种上下文里各放一个两位计数器，从而区分“同一条分支在不同历史下的不同倾向”。它是 TAGE 之前的主流方案，思想被 TAGE 继承。
- **TAGE 预测器**：通过多张使用**不同长度全局分支历史**的表，来捕捉从近期到远期的复杂相关性。预测时，它会选择匹配到**最长历史**的表的结果，以获得最高的准确率。

> 这里要分清：两位计数器、两级自适应、TAGE 都是**方向**预测器，不负责猜目标；给它们提供“分支在哪儿、目标是什么”的是 BTB（见 §4.2）。

## 4.2 间接分支预测（猜目标）

> 本节只讲“猜目标”的整体思路；论文里那台“两级间接分支预测器”的具体机制、以及它和 §4.1 两级自适应预测器的区别，见 §4.3。

间接分支（Indirect Branch）的目标地址来自**寄存器或内存**（`ret` 还来自栈），在运行时可能不断变化。这意味着**同一条指令可能对应多个不同的目标**，因此预测的核心任务是**预测目标地址**。

对应的**间接分支预测器**需要更复杂的机制：

- **传统方案**：主要依赖**分支目标缓冲区（BTB）**，缓存“某条分支上次跳到了哪儿”。要注意 BTB 是两类分支**共用**的基础设施：对条件直接分支，方向由方向预测器给，目标**在指令编码里、译码后可算出**；BTB 只是在取指阶段提前给出目标预测以加速重定向。对间接分支，目标**不在指令里**，BTB/ITTAGE 才是真正的目标预测器。代价是简单 BTB 一条分支通常只记一个目标，多目标场景下力不从心（目标一换就错）。
- **现代方案（ITTAGE）**：借鉴了 TAGE 的思想，使用全局分支/路径历史来索引多个预测表，以捕捉不同上下文下的目标地址模式，从而精准预测间接跳转的目的地。它的本质是一个针对分支目标地址的**值预测器**。
- **特殊成员：返回地址栈（RAS）**：对于函数返回（`return`）这类规律性极强的间接分支，硬件会使用一个专用的**返回地址栈**来精确预测返回地址，这是间接分支预测的一种高效特例。

> 论文统计“间接分支”时通常**不计入** `ret`，因为 RAS 让这类分支几乎不会误预测。

## 4.3 间接分支的“两级预测器”：和直接分支的“两级自适应”不是一回事

论文 §4.1.2 里表现最好的 **two-level predictor（Driesen & Hölzle, ISCA-98）**，和本笔记 §4.1 的“两级自适应预测器”（Yeh & Patt）**同名不同物**，读论文时千万别混：

| | §4.1 两级自适应（方向） | §4.3 两级间接预测器（目标） |
| --- | --- | --- |
| 猜什么 | 跳不跳 | 跳到哪里 |
| 历史寄存器存什么 | 分支**结果**比特（taken/not taken 串） | 最近 n 个**目标地址** |
| 索引 key | 分支地址 + 结果历史 | 分支地址 + 目标历史 |
| 表项内容 | 两位饱和计数器 | 预测目标 + 两位计数器 |

它的演进谱系（论文用它和 BTB 对比）：**BTB（记上次目标）→ BTB2（误预测两次才替换表项，1993 年随 Pentium 上市，长期是商用 CPU 里最先进的手段）→ 目标历史两级预测器（BTB2 相当于历史长度 0 的特例）→ 现代的 ITTAGE**。

论文测到的效果差距：threaded code 下 BTB/BTB2 误预测率 50%–63%，而目标历史两级预测器通常 <10%；switch dispatch 下 BTB/BTB2 几乎失效（98%），两级预测器照样好——因为它不依赖“每个指令一个跳转点”这个前提（见 §2.6.1）。

## 4.4 历史寄存器什么时候更新：speculative vs committed（论文自己的贡献点）

目标历史两级预测器有一个实现上的坑：**间接分支的真实目标要到指令提交（commit）之后才确定**（目标来自寄存器/内存，前面 §2.4 讲过），可是下一条分支的预测在取指阶段就要用历史寄存器。历史到底记什么？论文区分了三种做法：

- **理论版（研究文献里的默认）**：历史 = 最近 n 个**真实**目标。Driesen & Hölzle 没研究这个坑，因为他们用的是 **trace-driven 模拟**（回放执行轨迹，天然知道真目标）；用 **execution-driven 模拟**（模拟真实执行流，预测器只能看到硬件看得到的信息）才会暴露这个问题。这也是读仿真实验论文时要分的两组词：**cycle-accurate**（逐周期精确模拟）与 execution-driven / trace-driven。
- **2-level-speculative**：预测了就马上把**预测目标**推进历史（推测更新）；误预测时**不回滚**。优点是历史即时可用，缺点是猜错会污染历史、可能连着错一串。
- **2-level-commited**：等指令提交后把**真实目标**推进历史。优点是历史干净，缺点是更新滞后——下一条分支可能已经用旧历史做完预测了。

论文的结论：历史长度够（几个）时两种都还不错，但**谁更好因基准而异**，暗示可以把两者组合成混合预测器（hybrid predictor）。这段对应论文 §5.1、§5.2.6，是它声称“前人没研究过”的问题；和本笔记 §4.5 的方向预测器 GHR 回滚是同一类难题的不同解法——那边可以精确回滚，这边论文测的是“不回滚”和“迟到更新”两种务实方案。

## 4.5 误预测之后：恢复流程

不管方向错还是目标错，恢复动作是同一套：

1. **冲刷**流水线中错误路径上的指令（作废其在途状态）；
2. **重定向** PC 到正确目标；
3. 从正确地址**重新取指**，重新填满流水线；
4. **修正推测的分支历史（GHR）、更新预测器表项**——预测器每次分支解析后都会更新，但误预测后还要把“沿着错误路径推测出来的历史”恢复到正确路径上，否则会连着错。

这段“发现错误 → 重新填满”的时间就是**误预测惩罚**，机制详见 §2.4；它和“停顿”的区别见 §2.3.4。

## 4.6 小结

- 直接分支：目标已知，只赌**方向**，靠两位计数器 + 两级自适应 + TAGE；
- 间接分支：方向通常总是 taken，赌的是**目标**，靠 BTB → BTB2 → 目标历史两级预测器 → ITTAGE 这类**目标预测器**；
- `ret` 交给 RAS 特判，几乎不会误预测；
- 间接分支预测器有个特殊难题：**真实目标要等提交才知道**，所以历史更新只能选“推测更新不回滚”或“提交后迟到更新”；
- 两类误预测的恢复代价相同，都与“取指到分支解析的级数”成正比。

这也正好接回论文主线：解释器 dispatch 属于间接分支，而且目标数量多、分布随 opcode 变化，是分支预测器最难受的场景；threaded code 之所以有效，就是把“一个跳转点 → 多目标”拆成“多个跳转点 → 少目标”，让 BTB 重新能按 PC 区分。而预测器再强也需要硬件支持——下一章讲硬件和 ISA 层面还有哪些办法降低间接分支的代价。

# 五、让间接分支变快的架构手段（论文第 4 章）

前四章讲的是“**猜得更准**”。论文 §4 的出发点是：猜不准的时候，还可以**从硬件/指令集层面降低猜错的代价**。这是读这篇论文最容易漏掉的一条主线。

## 5.1 先给问题定位：为什么分支比普通指令贵

普通 ALU 指令：结果在执行阶段末尾出来，后面的指令也在执行阶段开头用它 → 依赖延迟约 1 周期，转发就能接上。

条件分支和间接分支：结果往往要等到**很靠后的流水级**才出来——论文给了具体数字：**Pentium III 第 10 级、Pentium 4 第 17 级**才解析分支，而它影响的是**第 1 级取指**。于是跳转后新取的指令要爬很多拍才能到执行级，这就是误预测惩罚。

还有一句要记住：“**直到 2003 年，仍有商用 CPU 完全不降低间接分支的代价**”，论文点名 AMD K6-2、MIPS R10000、UltraSPARC II——原文的说法是这几款“没有任何办法降低间接分支的代价（without any way to reduce the cost of indirect branches）”。

## 5.2 静态预测：ISA 给出目标提示（profile-guided）

**Alpha** 架构在 `JMP` 指令里放了一个字段，写入**预测目标的 16 位**（够定位 I-Cache 里的一条指令），编译器可以配合 profile 反馈填这个字段。

两个必须记住的局限：

1. **即使猜对了也有固定代价**：提示写在指令里，必须**先把这条指令译码**才能读到，所以“猜对”依然要付出到译码级之前的那几拍。→ 这条是“**静态/ISA 提示 vs 硬件动态预测**”的本质差别：动态预测（BTB）在取指阶段就能给答案，静态提示不行。
2. **软件支持跟不上**：gcc-2.95.2 的 `-fprofile-arcs` 不支持 computed goto；Compaq C 只处理 switch dispatch、只生成一条间接跳转，准确率被限制在约 10%。

论文 §6.2 的补充建议是：支持这个 hint 的架构应该让编译器把它用起来（最好带 profile 反馈），收益上限约 1.17 倍——很小。

## 5.3 降低代价之一：延迟分支（delayed branch）

**定义**：跳转指令不立即生效，而是先执行紧随其后的**延迟槽（delay slot）**里的指令，再跳。这样硬件有额外时间算出真实目标，**猜错也不浪费**——延迟槽里的指令本来就是要执行的。

这正是本笔记 §2.6.1 那段 MIPS 汇编里 `#nop` / `#branch delay slot` 注释的来历：MIPS 每条跳转后面都有一个延迟槽，编译器填不满就塞 `nop`。

- **为什么桌面/服务器架构放弃了它**：延迟槽**数量依赖具体实现**（不同机器可能 1 个或更多），会**破坏二进制兼容性**——同一份机器码在不同机器上语义可能不同。
- **为什么嵌入式还在用、而且解释器很受益**：嵌入式 ISA 通常固定延迟槽，编译器能精确安排；解释器的 dispatch 序列结构固定，非常适合把有用指令塞进槽里。

## 5.4 降低代价之二：分离式分支（split branch / prepare-to-branch）

比延迟分支更灵活（不依赖实现的槽数）：**把“准备好目标”和“真正跳转”拆成两条指令**。

- **Power/PPC**：`mtctr`（把目标装进分支寄存器 CTR）+ `bctr`（真正跳转）。初代 Power 实现里两条指令之间延迟 **5 周期**，这 5 拍用来把地址送进分支单元、并提前开始取指/译码目标；而真正的控制转移**立即发生**。
- 同族机制：**HP PlayDoh**、**IA-64** 都用“指定分支寄存器”的 prepare-to-branch。
- **PPC 的另一对**：`mtlr`/`blr` 专用于返回地址，PPC 7450 还会用返回栈预测 `blr`。

## 5.5 关键难点：目标依赖 load + 内存依赖（这条最重要）

**问题**：解释器的间接跳转目标来自一条 load（`lw` 从 VM 指令流里取 handler 地址）。用延迟分支或分离式分支时，处理器必须先把这条 load **取指、译码、执行完**，跳转才可能生效。于是一条 VM 指令至少要花“load 从取指级到结果级”那么久。

**解法：把 load 提前到上一条 VM 指令里做**——即对解释器做**软件流水线（software pipelining）**。但跨跳转移动 load 会带来一个约束：**必须重命名结果寄存器**（否则上一条和下一条指令会把同一个寄存器写坏）。两条路：

1. **插一条 move 指令**（PowerPC/PlayDoh/IA-64 的 prepare-to-branch 本身就是一种 move，不用额外指令）；但这条 move 仍然要被取指、译码、执行完跳转才生效 → 得到一条 VM 指令的**最短时间：取指 + 译码 + 执行 move，然后执行间接跳转**。
2. **把整个解释器复制一份做变量重命名（modulo variable renaming）**——太复杂，threaded code 下尤其难。

现实障碍：编译器支持不佳，gcc-2.95 不会尽早安排 prepare-to-branch 指令。

## 5.6 还有一个隐藏杀手：store→load 依赖

论文 §5.2.3 测到“运行时间随误预测惩罚**近乎线性**上升”，这个结果连作者都意外。原本期望：dispatch 的依赖链很短（每条 VM 指令只更新一次指令指针），给足取指/译码带宽，dispatch 就能跑到前面，用重叠把误预测的开销掩盖掉——那样低惩罚区间曲线应该变平。

实际掩盖不了，原因是：**dispatch 里那条 load 依赖前面 VM 指令执行过程中的 store**——栈式 VM 的栈溢出写回（stack spill）、寄存器式 VM 的结果寄存器写入。**在地址未知的 store 完成之前，load 不能提前执行**，于是整条 dispatch 被卡在数据依赖上，只能等。

要补的知识（本笔记原来完全没有）：

- **store→load 依赖 / 内存别名（memory aliasing）**：load 的地址和某条 store 的地址是否相同，硬件在编译期往往看不出来（两个指针可能指向同一块内存）。
- **store-to-load forwarding（转发）**：store 把数据写进 store buffer，命中同一地址的 load 可以直接从 store buffer 取数据。
- **推测执行 load**：更高级的机器允许 load 在结果未知时**投机**先取旧值，事后校验；论文说这类处理器上应该能看到略微不同的结果。

## 5.7 一个非常好用的等价关系

由“近乎线性”可以推出论文里最实用的一句话：

> **把误预测次数（所有分支）减半，等价于把误预测惩罚减半**（包括间接分支所依赖的未完成指令的延迟）。

结论：在“只有 BTB 类硬件”的现状下，**加一个两级间接分支预测器**比**设法缩短惩罚**更容易把解释器提速——这也是论文 §6.1 给硬件设计者的首要建议：对高效解释器最有用的硬件支持就是**好的间接分支预测**（两级预测器相对 BTB2 可提速 1.97 倍 @4 周期惩罚、3.08 倍 @13 周期惩罚）。

## 5.8 读这篇论文实验时的三个方法学坑

1. **预测表容量设成“无限大”**：论文故意不给 BTB / 两级预测器设实际上限，因为固定容量的配置会带来**冲突缺失（conflict miss）**这类假象，换台机器或改几行代码结论就变；而且对两级预测器来说，无限容量的结果已经接近“调得好、表够大”的真实硬件（论文 §5.1）。所以论文里的准确率是**上界**，真实硬件会更低。
2. **惩罚是怎么模拟出来的**：SimpleScalar 直接改 mispredict penalty 数值。作者明确说，把惩罚调大可以**看成“模拟一条取指/译码级数更多的流水线”**；而它默认的“最小惩罚”是 4 周期（SimpleScalar 内部叫 1 周期，论文全文用传统口径的 4 周期）。看到“4 cycles / 1 cycle”这种不一致，是术语口径问题，不是数据错误。
3. **真实机器只能用性能计数器间接测量**：Athlon 的 PMU 数不出“间接分支”这个事件，作者只能用 **taken branch 做近似**，所以才挑 gforth-benchgc（直接分支很少，近似最准）。引用 §5.2.7 的数字时要带上这个口径限制。另外，动态复制 handler / 动态超级指令这类做法需要在目标机器上**刷新 I-Cache**，所以要用到 target-specific 代码，还要多花内存（§6.3）。

## 5.9 小结

降低间接分支代价有两条正交的路：**猜得更准**（BTB → BTB2 → 目标历史两级预测器 → ITTAGE，见第四章）和**猜错更便宜**（延迟分支、分离式分支、ISA 目标提示，见本章 §5.2–5.4）。但软件侧的真正制约是**数据依赖**：目标来自 load，而 load 又依赖前面的 store（§5.6）。这解释了为什么论文的惩罚—时间曲线是线性的。也解释了软件手段为什么有效，但要分清两者机制不同：**复制 handler** 是把“一个跳转点→多目标”拆成“多个跳转点→少目标”（改善的是预测条件，§2.6.1），**超级指令**则是直接消灭了一部分间接分支（减少的是分支次数，配合 §5.7 的等价关系就是提速）。
